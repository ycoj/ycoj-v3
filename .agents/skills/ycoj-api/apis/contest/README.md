# Contest routes and operations

All routes are domain-aware. `PERM_VIEW_CONTEST` gates public reads; management handlers enforce the endpoint-specific ownership and edit permissions documented below. Operation-specific permissions (print, user, scoreboard, etc.) are checked in the implementation. Ordinary browser GETs render HTML/PJAX; plagiarism endpoints and scoreboard export data return JSON directly. Named POST operations are selected by the body `operation` field; endpoints with a plain POST method, such as plagiarism admission, use the body documented for that endpoint. Do not invent `/postXxx` URL suffixes.

## Routes

Existing contest create/edit fields, default scoreboard Rating results, profile history and automatic replay: [rating.md](rating.md).

`GET /contest?rule?:RULE&group?:Name&page?:PositiveInt&q?:string` -> `contest_main.html`, `{ tdocs,page,tpcount,groups,q }`.

`GET /contest/:tid` -> `contest_detail.html`, `{ tdoc,tsdoc,pids,pdict,psdict,rdict,rdocs,udoc,... }`. Authorized viewers also receive a compact contest-solution table (title, author, time) under the introduction; see [contest-solutions.md](contest-solutions.md). POST operations: `attend` (`code?:string`), `subscribe` (`subscribe:boolean`), `earlyEnd` (manager). They return back/redirect responses. `GET /contest/:tid/problems` -> problem list/PJAX; after the contest starts and before it ends, an unattended contest owner or user with contest-edit/hidden-contest-view permission may inspect this list only. Not-started contests are rejected with `ContestNotLiveError`, including for those authorized users. The exception does not extend to contest problem details or mutations. POST `clarification` uses `{ content:Content, subject:Int }` and still requires attendance.

`GET/POST /contest/:tid/solution/create`, `/contest/:tid/solution/:sid`, and `/contest/:tid/solution/:sid/edit` expose titled Markdown contest solutions. Full contract: [contest-solutions.md](contest-solutions.md).

`GET /contest/create` and `/contest/:tid/edit` render edit form. The edit response also returns `code`, the invitation code stored as `_code` on `tdoc` but stripped from serialized documents. POST fields: `{ tid?:ObjectId; beginAtDate:Date; beginAtTime:Time; duration:Float; title:Title; content:Content; rule:string; pids:Content; rated:boolean; code?:string; autoHide:boolean; assign?:string[]; lock?:UnsignedInt; contestDuration?:Float; maintainer?:number[]; allowViewCode:boolean; allowPrint:boolean; keepScoreboardHidden:boolean; langs?:string[] }`. Response `{ tid:ObjectId }` and redirect `/contest/:tid`. `delete` operation redirects `/contest`.

`GET /contest/:tid/print` and `/api/printing/team` render print HTML. POST operations `print` (`title?,content?`) returns `{success:boolean,output:string}`; `getPrintTask` -> `{tasks,udict}`; `allocatePrintTask` -> `{task,udoc}`; `updatePrintTask` (`taskId,status:"printed"|"pending"`) -> `{success:true}`. Print failures return `{success:false,output}` without redirect.

JSON operation `rejudge` on `POST /contest/:tid/management` queues all eligible contest submissions and returns `{count:number}`; requires ownership/maintainership or `PERM_EDIT_CONTEST`, excludes canceled records and hacks, and validates configurations before resetting. See [the rejudge contract](endpoints.md#post-contesttidmanagement-operation-rejudge) for side effects and monitoring. `GET /contest/:tid/management` -> management HTML/PJAX with complete contest problem documents in `pdict`, including statement content, judge config, data files, additional files, and references. Multipart operations `uploadFile` (`filename`, `type?:public|private`, file), `deleteFiles` (`files[]`, type), and JSON `setScore` (`pid:PositiveInt,score:PositiveInt`) redirect/back or return operation JSON. `GET/POST /contest/:tid/bulk-submit` is documented in [bulk-submit.md](bulk-submit.md): GET renders the mapping form and uses each file-IO problem's filename as its default zip problem name (only the first of duplicate filenames is prefilled); POST uploads a contestant zip (`mapping` JSON of website pid → zip problem name, optional C++ `lang`, optional `dryrun`, optional `existingUser` `"vuser"|"existing"` default `"existing"`, optional `zipMode` `"auto"|"subfolder"|"nosubfolder"` default `"auto"`). The server inspects the zip with lookup-only identity (no user/contest/record writes); dryrun returns that report (`users[].kind`, optional `realUid`, planned new vuser `uid: 0`) without mutating contest state. Commit attends each contestant who has at least one ready file and writes those files through `record.add`, which creates and queues the judge task, followed by the normal counter/status updates. Record, queue, counter, or status failures are returned as per-entry skips; persisted records are not rolled back and retries are not idempotent. `GET /contest/:tid/clarification` renders clarification management; POST `clarification` accepts `{content,did?:ObjectId,subject?:Int}`.

`GET/POST /contest/analysis`, `GET /contest/analysis/:aid`, and `POST /contest/analysis/:aid` (`cancel`, `delete`, `retry`) run an asynchronous AI analysis of one to twelve finished contests and return one report per selected contest plus one per student. Problem snapshots include raw statement content; the agent can read statements to infer missing tags/difficulty, identifying estimates in report text while preserving snapshot metadata. Creating a job requires contest-management permission on every selected contest; reading or changing a job requires `PERM_EDIT_CONTEST` or the creating user. Full contract: [analysis.md](analysis.md).

`GET/POST /contest/:tid/plagiarism`, `GET /contest/:tid/plagiarism/:jobId`, and `GET /contest/:tid/plagiarism/:jobId/source/:rid` provide persistent asynchronous C++ similarity checks and authorized analyzed-source snapshots after the global contest ends. Every call requires `PERM_EDIT_CONTEST_SELF` for owners/maintainers or `PERM_EDIT_CONTEST` for non-owners; neither ownership nor the broader permission bypasses the applicable check. POST accepts `{method?: 'tree-sitter' | 'heuristic'}` (Tree-sitter by default), returns HTTP 202, and reuses an active task for this contest with its original method. Jobs and reports identify their method. Reports retain the 100 largest matching regions per pair in source order. Full schemas, limits, failure/retention behavior, and examples are in [plagiarism.md](plagiarism.md).

`GET /contest/:tid/code?all:boolean` returns code-view HTML/model. `GET /contest/:tid/file/:type/:filename?noDisposition:boolean` redirects to a signed binary URL (`type=public|private`). `GET /contest/:tid/user` -> `{tdoc,tsdocs,udict}`; operations `addUser` (`uids:number[],unrank?`), `rank` (`uid`), `resume` (`uid`), `removeUser` (`uid`). `GET /contest/:tid/balloon?todo:boolean` -> balloon HTML/model; operations `setColor` (`color`) and `done` (`balloon:ObjectId`).

`GET /contest/:tid/scoreboard[/:view]` renders scoreboard data/HTML; POST `unlock` returns a redirect/back result after management permission. Browser-negotiated page requests render HTML, signed-file redirects become JSON `{url}` under JSON negotiation, and endpoints that explicitly call `binary()` remain binary.

## Common request/response contract

Authenticate with `Cookie: sid=...` or `Authorization: Bearer <sid>`; JSON clients send `Content-Type: application/json`, while upload operations require `multipart/form-data`. Object IDs are 24-hex strings. With `Accept: application/json`, logical redirects serialize as HTTP 200 `{ "url":"/..." }`; normal browsers receive redirects. Successful JSON examples: `{ "tid":"665f00000000000000000001", "url":"/contest/665f00000000000000000001" }`, `{ "success":true }`, `{ "tasks":[],"udict":{} }`. Validation errors identify the decorated field; failed permission checks are rejected before model mutation.

Image export: `GET /contest/:tid/scoreboard/export-data?details=true` and `/homework/:tid/scoreboard/export-data?details=true` provide authorized real names and per-participant submission journals. See [the export contract](../contest/endpoints.md#image-export-data).
